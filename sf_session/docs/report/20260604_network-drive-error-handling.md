# ネットワークドライブ障害時の挙動

## 概要

このプロジェクトはマクロファイルや CSV の出力先にネットワークドライブを使う。
ネットワーク障害時の挙動は「いつ切れたか」によって3段階で対処する。

```
起動前に切れてた          → home fallback で起動
実行中に一時的に切れた    → _move_with_retry で自動復旧
実行中に長時間切れた      → 失敗ログ → --retry で再実行
```

---

## 段階 1: 起動前にネットワークドライブが見えない

### 何が起きるか

`config.py` が import される時点（起動時）に `MACRO_ROOT_PATH` の到達性を1回だけチェックする。
ネットワークドライブが見つからない場合、`USE_HOME_FALLBACK = True` が立ち、
以降のすべての path 解決で `~/` 配下へ fallback する。

```
MACRO_ROOT_PATH=Z:\Users\you\macros
  ↓ Z: が存在しない
~/Users/you/macros   ← に fallback して動作継続
```

### なぜこれで動くか

ネットワークドライブ（Z:）はローカルの `~/` をマウントしているだけなので、
物理的には同じ場所を指している。Z: 経由でも `~/` 経由でも同じファイルに届く。

### 実装箇所

`sf_session/config.py` — `resolve_project_path()` / `USE_HOME_FALLBACK`

---

## 段階 2: 実行中に一時的に切れた

### 何が起きるか

ファイルの移動（`shutil.move`）が `OSError` を投げる。
`_move_with_retry()` が最大3回、3秒間隔でリトライする。

```
移動失敗 → 3秒待機 → リトライ
移動失敗 → 3秒待機 → リトライ
移動失敗 → 諦めて OSError を raise
```

最大 9 秒の間に復旧すれば、ユーザーは気づかず処理が続く。

### 実装箇所

`sf_session/download/runner.py` — `_move_with_retry()`

---

## 段階 3: 実行中に長時間切れた

### 何が起きるか

3回のリトライがすべて失敗すると、そのジョブは失敗として記録される。
処理は続行し、残りのジョブを実行する（1件の失敗で全体が止まらない）。

実行後に失敗件数がログに出力される：

```
失敗 2 件 / 成功 8 件
[NG] 3件目 00O000003: ファイル移動失敗: ...
[NG] 7件目 00O000007: ファイル移動失敗: ...
```

### 再実行方法

```powershell
py -m sf_session.download <pipeline> --retry
```

`--retry` は前回の `success_ids` を読み、成功済みのジョブをスキップして失敗分だけ再実行する。
ネットワークが復旧してから実行すれば、失敗分だけ効率よく補完できる。

---

## まとめ

| タイミング | 原因 | 対処 | ユーザー操作 |
|---|---|---|---|
| 起動前 | ドライブが見つからない | `~/` に fallback して起動 | 不要 |
| 実行中（一時的） | 瞬断・短時間の切断 | `_move_with_retry` で自動リトライ | 不要 |
| 実行中（長時間） | 長時間の切断 | 失敗ログを記録して続行 | `--retry` で再実行 |
